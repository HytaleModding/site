## `Store`

A classe `Store` é o núcleo do sistema ECS do Hytale. Ela é responsável por armazenar entidades. Sempre que você precisar acessar uma entidade, será necessário ter acesso ao `Store`. Ele utiliza um conceito chamado Arquétipos (Archetypes), no qual os dados são agrupados em blocos (chunks). Por exemplo, se tivermos 100 Trorks, eles serão agrupados juntos com seus componentes, de forma que fiquem compactados e mais rápidos de acessar.

## `EntityStore`

Ao analisar o código do servidor do Hytale, você perceberá que, na maioria das vezes, o `Store` será do tipo `EntityStore`. Esse nome pode ser um pouco enganoso, pois pode sugerir que ele é um `Store` apenas de entidades.
Mas não acabamos de dizer que o `Store` base já armazena entidades? A classe `EntityStore` implementa `WorldProvider`, o que significa que o `EntityStore` é responsável por acessar um `World` específico do Hytale. Ele mantém mapas internos, como `entitiesByUuid` e `networkIdToRef`, permitindo que você encontre uma entidade específica pelo seu ID persistente ou pelo seu ID de rede.

Toda entidade possui um `UUIDComponent` e um `NetworkId`, que são utilizados pelo `EntityStore` para localizar entidades dentro do `Store`.

## `ChunkStore`

Outro tipo de `Store` que você pode encontrar é o `ChunkStore`. Ele é responsável por armazenar todos os componentes relacionados aos blocos dentro do `World`. A partir dele, você pode recuperar `WorldChunks`, que são os componentes gerais de chunks.
Um componente `WorldChunk` contém um `EntityChunk`, que mantém todas as `Entities` dentro daquele chunk, além de suas referências ao `EntityStore`. Ele também contém o `BlockChunk`, que é composto por `BlockSections`. Existem mais componentes que formam os sistemas gerais de mundo e de chunks, mas, por enquanto, essa é a compreensão básica do `ChunkStore`. Você pode utilizá-lo para obter dados sobre chunks e seus blocos, bem como entidades em um determinado chunk, e para criar sistemas de blocos e chunks.

## `Holder`

Um `Holder` é essencialmente um blueprint de uma entidade. Antes de uma entidade existir na Loja, e no mundo, ela existe como um `Holder`. Ele coleta e mantém todos os componentes (dados) necessários. Você pode compará-lo a um carrinho de compras: você pega todos os componentes de que precisa e, quando tiver tudo pronto, finaliza no caixa do `Store`, que irá pegar seu carrinho, criar um ID de entidade válido e devolver um recibo (um `Ref`).

Vamos ver um exemplo: a inicialização de jogadores. Na classe `Universe`, o método `addPlayer` demonstra isso perfeitamente.
Quando um jogador se conecta, não o inserimos imediatamente no ECS. Primeiro, construímos seus dados em um `Holder`.
Observe que o método `PlayerStorage#load`, que carrega os dados do jogador do disco, retorna um `CompletableFuture<Holder<EntityStore>>`.
Isso significa que o método é assíncrono e que o future conterá um `Holder` para algo no `EntityStore`.
Basta abrir a classe `Universe`, localizar o método `addPlayer` e lê-lo do início ao fim. Confie em mim, isso vai ajudar muito quando você enxergar o processo real de como uma entidade é construída e por tudo o que ela passa. No final, o `Universe` chama `world#addPlayer`, que (após despachar um evento) executa a seguinte linha:

```java
Ref<EntityStore> ref = playerRefComponent.addToStore(store);
```

E o método `PlayerRef#addToStore` contém:

```java
store.addEntity(this.holder, AddReason.LOAD);
```

## `Ref` (Referência)

Para quem já está familiarizado com linguagens como C++, provavelmente já é possível adivinhar o que essa classe representa apenas pelo nome. Um `Ref` é um "handle" ou ponteiro seguro para uma entidade. Você **NUNCA** deve armazenar uma referência direta a um objeto de entidade; em vez disso, utilize um `Ref`. Ele rastreia se a entidade ainda está viva. Se você chamar `validate()` em um `Ref` de uma entidade que já foi removida, uma exceção será lançada.

## Componentes de `Player`

No Hytale, um "Player" não é apenas um único objeto. Ele é uma única entidade composta por múltiplos componentes especializados. Entender a diferença entre `Player` e `PlayerRef` é fundamental para modificação.

### `PlayerRef`

Apesar do nome, `PlayerRef` é um `Component`, não um handle. Ele representa a conexão e a identidade do jogador. É um componente especial que permanece ativo enquanto o jogador estiver conectado ao servidor, mesmo que ele troque de mundo. Os principais dados que ele armazena são o nome de usuário do jogador, o UUID, o idioma e o packet handler.

### `Player`

O componente `Player` representa a presença física do jogador. Ele só existe quando o jogador está efetivamente spawnado em um mundo. Fornecendo acesso a dados específicos de gameplay, esse componente varia de acordo com o mundo.

Para interagir com uma entidade, você utiliza o `Store` para recuperar seus componentes por meio do `ComponentType`. Como o Hytale utiliza um sistema desacoplado, você não chama `entity.getHealth()`. Em vez disso, você solicita ao `Store` os dados de vida associados ao `Ref` da entidade.

```java
@Override
protected void execute(@Nonnull CommandContext commandContext, @Nonnull Store<EntityStore> store,
    @Nonnull Ref<EntityStore> ref, @Nonnull PlayerRef playerRef, @Nonnull World world) {
  Player player = store.getComponent(ref, Player.getComponentType());
  UUIDComponent component = store.getComponent(ref, UUIDComponent.getComponentType());
  TransformComponent transform = store.getComponent(ref, TransformComponent.getComponentType());
  player.sendMessage(Message.raw("UUIDComponent : " + component.getUuid()));
  player.sendMessage(Message.raw("Transform : " + transform.getPosition()));
}
```

Aqui, utilizamos o `Store<EntityStore>` para acessar o componente `Player` usando o `Ref<EntityStore>`. Podemos fazer o mesmo para outros componentes, como o `UUIDComponent` ou o `TransformComponent`, para obter o `Transform` da entidade, que contém posição e rotação.

## `Components`

Os components são contêineres puros de dados. Eles mantêm o estado, mas não contêm lógica. No Hytale, componentes devem implementar `Component<EntityStore>` e fornecer um método clone para que o ECS possa copiá-los quando necessário.

```java
public class PoisonComponent implements Component<EntityStore> {

  private float damagePerTick;
  private float tickInterval;
  private int remainingTicks;
  private float elapsedTime;

  public PoisonComponent() {
    this(5f, 1.0f, 10);
  }

  public PoisonComponent(float damagePerTick, float tickInterval, int totalTicks) {
    this.damagePerTick = damagePerTick;
    this.tickInterval = tickInterval;
    this.remainingTicks = totalTicks;
    this.elapsedTime = 0f;
  }

  public PoisonComponent(PoisonComponent other) {
    this.damagePerTick = other.damagePerTick;
    this.tickInterval = other.tickInterval;
    this.remainingTicks = other.remainingTicks;
    this.elapsedTime = other.elapsedTime;
  }

  @Nullable
  @Override
  public Component<EntityStore> clone() {
    return new PoisonComponent(this);
  }

  public float getDamagePerTick() {
    return damagePerTick;
  }

  public float getTickInterval() {
    return tickInterval;
  }

  public int getRemainingTicks() {
    return remainingTicks;
  }

  public float getElapsedTime() {
    return elapsedTime;
  }

  public void addElapsedTime(float dt) {
    this.elapsedTime += dt;
  }

  public void resetElapsedTime() {
    this.elapsedTime = 0f;
  }

  public void decrementRemainingTicks() {
    this.remainingTicks--;
  }

  public boolean isExpired() {
    return this.remainingTicks <= 0;
  }
}
```

O construtor padrão é obrigatório para a fábrica de registro. O construtor de cópia é utilizado pelo método `clone()`, que o ECS chama internamente quando precisa duplicar dados de componentes.

## `CommandBuffer`

O `CommandBuffer` enfileira alterações em entidades. Utilize-o em vez de modificar o `Store` diretamente, para garantir segurança de threads e ordenação correta. Você o utilizará para adicionar componentes, remover componentes e executar dano.

```java
commandBuffer.addComponent(ref, componentType, new MyComponent());

commandBuffer.removeComponent(ref, componentType);

MyComponent comp = commandBuffer.getComponent(ref, componentType);
```

## Codec

Os codecs lidam com a serialização e desserialização de componentes. O Hytale os utiliza para salvar e carregar dados de entidades do disco, além de enviar dados de componentes pela rede. Ao criar um componente personalizado, você também deve criar um codec correspondente.

Existem vários tipos de codecs já implementados na interface de codecs padrão:

- Codec.STRING
- Codec.BOOLEAN
- Codec.DOUBLE
- Codec.FLOAT
- Codec.BYTE
- Codec.SHORT
- Codec.INTEGER
- Codec.LONG
- Codec.DOUBLE_ARRAY
- Codec.FLOAT_ARRAY
- Codec.INT_ARRAY
- Codec.LONG_ARRAY
- Codec.STRING_ARRAY
- Codec.PATH
- Codec.INSTANT
- Codec.DURATION
- Codec.DURATION_SECONDS
- Codec.LOG_LEVEL
- Codec.UUID_BINARY
- Codec.UUID_STRING

Além dos tipos básicos, também existem implementações mais complexas, como `CodecMap`, `ObjectMapCodec` e `EnumCodec`.

### Builder Codec

O `BuilderCodec` é uma ferramenta poderosa para criar _codecs_ customizados. Ele permite definir como cada campo do seu componente será serializado e desserializado. Cada campo precisa conter as seguintes informações:

- O `KeyedCodec` usado para serialização e desserialização do campo. Ele pode ser um _codec_ interno ou um _codec_ customizado, caso o campo seja um tipo complexo. Para inicializar um `KeyedCodec`, é necessário fornecer um identificador de _string_ único e a instância do `Codec` que será usada.

<Callout type="warning">
Tenha em mente que todo identificador de `KeyedCodec` deve começar com letra maiúscula e ser único em todo o seu mod. Isso significa que, se você tiver múltiplos componentes, o identificador de cada campo não pode entrar em conflito com o identificador de qualquer outro campo de qualquer outro componente dentro do mod. Caso contrário, você poderá enfrentar problemas de serialização.
</Callout>

- Uma função setter para definir o valor do campo no componente;
- Uma função getter para recuperar o valor do campo a partir do componente.

Isso pode parecer trabalhoso no início, mas garante que seu componente possa ser corretamente serializado e desserializado pelo sistema ECS. Vamos analisar cada um dos parâmetros necessários em detalhes:

- **KeyedCodec**: Define como os dados são convertidos de e para um formato armazenável. Por exemplo, se você tiver um campo inteiro, deverá usar `Codec.INTEGER`.
  ```java
  // Exemplo de criação de um KeyedCodec para um campo String
  KeyedCodec<String> example = new KeyedCodec<String>("ExampleIdForCodec", Codec.STRING);
  // Exemplo de criação de um KeyedCodec para um campo Integer
  KeyedCodec<Integer> exampleInt = new KeyedCodec<Integer>("ExampleIntIdForCodec", Codec.INTEGER);
  ```

- **Função setter**: Esta é uma função lambda que recebe uma instância do seu componente + o valor a ser definido e define o valor do campo no componente. Por exemplo, se você tiver um campo chamado `myCustomField` em seu componente personalizado, sua função setter ficaria assim:
  ```java
  (data, value) -> data.myCustomField = value
  ```

- **Função getter**: É uma função lambda que recebe uma instância do seu componente e retorna o valor do campo. Por exemplo, se você tiver um campo chamado `myCustomField`, o _getter_ ficaria assim:
  ```java
  (data) -> data.myCustomField
  ```

<Callout type="info">
As funções lambda são uma forma concisa de representar interfaces funcionais em Java. Elas permitem passar comportamento como parâmetro, tornando o código mais flexível e reutilizável. No contexto da criação de _codecs_, elas permitem definir como obter e definir valores de campos sem a necessidade de criar classes ou métodos separados para cada campo.

Se você não estiver familiarizado com funções lambda, pode enxergá-las como métodos curtos e compactos definidos inline. Elas são especialmente úteis em cenários em que é necessário passar um comportamento simples, como obter ou definir um valor, sem a sobrecarga de criar uma classe ou método completo.

Como exemplo, considere a seguinte função lambda usada como _getter_:
```java
(data) -> data.myCustomField
```

Essa lambda recebe um único parâmetro `data` (que seria uma instância do seu componente) e retorna o valor de `myCustomField`. Ela é equivalente a escrever um método como este:
```java
public Object getMyCustomField(MyComponent data) {
    return data.myCustomField;
}
```
</Callout>

Após definir os parâmetros necessários, você pode criar um `BuilderCodec` para o seu componente. Como exemplo, veja como criar um _Codec_ para o `PoisonComponent` definido anteriormente. Para a proposta desse exemplo, vamos assumir que o `PoisonComponent` possui apenas os seguintes campos:

- `damagePerTick` (float)
- `poisonName` (String)

```java
public class PoisonComponent implements Component<EntityStore> {
    private float damagePerTick;
    private String poisonName;

    // Construtores, getters, setters e método clone omitidos por brevidade

        public static final BuilderCodec<PoisonComponent> CODEC = BuilderCodec.builder(PoisonComponent.class, PoisonComponent::new)
            .append(
                new KeyedCodec<Float>("DamagePerTick", Codec.FLOAT),
                (data, value) -> data.damagePerTick = value,
                (data) -> data.damagePerTick
            )
            .add()
            .append(
                new KeyedCodec<String>("PoisonName", Codec.STRING),
                (data, value) -> data.poisonName = value,
                (data) -> data.poisonName
            )
            .add()
            .build();
}
```

Você também pode adicionar validadores aos campos do _Codec_ para garantir que os dados serializados e desserializados atendam a determinados critérios. Por exemplo, para garantir que o campo `damagePerTick` seja sempre não negativo ou que o nome do veneno nunca seja nulo, você pode usar validadores como estes:

````java
.append(
    new KeyedCodec<Float>("DamagePerTick", Codec.FLOAT),
    (data, value) -> data.damagePerTick = value,
    (data) -> data.damagePerTick
)
.addValidator(Validators.greaterThan(0))
.add()

.append(
    new KeyedCodec<String>("PoisonName", Codec.STRING),
    (data, value) -> data.poisonName = value,
    (data) -> data.poisonName
)
.addValidator(Validators.nonNull())
.add()

### Exemplos de codecs complexos

Se você deseja ter um mapa dentro do seu componente, pode usar a classe `MapCodec` para criar um `KeyedCoded` para ele. Aqui está um exemplo de como criar um Codec para um campo de mapa:

```java
var damagePerTick = new KeyedCodec<>("DamagePerTick", new MapCodec<>(Codec.FLOAT, HashMap<String, Float>::new));
````

### Exemplos de Codecs Complexos

Se desejar ter um mapa dentro do seu componente, pode usar a classe MapCodec para construir um KeyedCodec para ele. Aqui está um exemplo de como criar um Codec para um campo de Mapa (Map):

```java
var damagePerTick = new KeyedCodec<>("DamagePerTick", new MapCodec<>(Codec.FLOAT, HashMap<String, Float>::new));
```

<Callout type="info">
Isso também funciona com objetos customizados, desde que você tenha um codec definido para o tipo do objeto.
</Callout>
